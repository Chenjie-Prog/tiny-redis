# 第 4 章：过期与持久化 —— 让数据活得下来

实现见 [`tinyredis/storage.py`](../tinyredis/storage.py)（过期）和
[`tinyredis/persistence.py`](../tinyredis/persistence.py)（持久化）。

## 过期：惰性 + 主动，两层删除

**存什么？** 绝对时间戳（Unix 秒，浮点毫秒精度），不是"剩余秒数"。
原因：快照恢复后，剩余时间应该从文件里的绝对时刻继续算——
存相对时间，重启一次 TTL 就重置一次。

**惰性删除**。任何访问先检查：

```python
def _purge(self, key):
    deadline = self._expires.get(key)
    if deadline is not None and time.time() >= deadline:
        self._expires.pop(key, None)
        self._data.pop(key, None)
    return key in self._data
```

`GET`、`EXISTS`、`TTL`……所有读路径都先过这一关，过期键等于不存在。

**主动过期**。惰性删除只处理"被访问的键"——大量设置了 TTL 但再也没人
访问的键会一直占内存。所以事件循环每 0.1 秒跑一次采样：

```python
def expired_cycle(self, samples=20, max_rounds=4):
    keys = list(self._expires)
    picked = random.sample(keys, min(samples, len(keys)))
    for key in picked:
        if now >= self._expires[key]:

```

真实 Redis 的策略更精细（过期比例 > 25% 就立刻再来一轮，最多循环 16 轮），
tiny-redis 简化成最多 4 轮——教学项目里，机制比参数重要。

## 持久化：TRDB 快照格式

Redis 的 RDB 是个紧凑的二进制格式。tiny-redis 造了一个教学版——**TRDB**，
保留 RDB 的核心思想（opcode 流 + 全文件校验），砍掉变长编码的复杂度：

```
"TRDB" "0001"          <- 8 字节魔数 + 版本
记录 ...
0xFF                   <- 结束操作码
CRC64 (8 字节大端)      <- 覆盖前面全部字节
```

一条记录：

```
[0xFC + 8字节过期毫秒时间戳]    <- 可选，只有带 TTL 的键有
1 字节类型                      <- 0x00 字符串 / 0x01 列表 / 0x02 哈希
键 bstr
值：字符串 = 1 个 bstr
    列表   = uint32 数量 + N 个 bstr
    哈希   = uint32 数量 + N 对 (bstr, bstr)
```

`bstr` = 4 字节大端长度 + 内容。比 RDB 的变长编码费几个字节，
换来的是三行就能讲清楚的解码逻辑。

## CRC64：把损坏挡在恢复之前

快照写到一半断电、磁盘坏块……都会让文件"缺胳膊少腿"。TRDB 在文件尾
附 CRC64 校验（CRC-64/XZ 变体，与 Redis 同款多项式的反射形式），
标准测试向量验证实现正确性：

```python
assert crc64(b"123456789") == 0x995DC9BBDF1939FA
```

表驱动实现二十行。加载时先验 CRC 再解析——**任何一位翻转都会被拒之门外**
（`test_flipped_byte_detected_by_crc` 验证了单字节翻转必被检出）。

## 写入的原子性

快照不能直接覆盖旧文件：写一半崩溃 = 旧快照也没了。标准做法是
**先写临时文件，再原子改名**：

```python
tmp = path.with_suffix(".trdb.tmp")
tmp.write_bytes(bytes(out))
os.replace(tmp, path)      # POSIX 上原子，Windows 上也接近原子
```

`os.replace` 保证读者看到的要么是完整的旧文件，要么是完整的新文件。

## 恢复时遇到的三个边界

1. **已过期的键**：直接跳过——但必须把值字节也读完，否则破坏后续
   记录的对齐（这是本项目真实踩过并写成测试的 bug）；
2. **TTL 的语义**：绝对时间戳恢复后自然就是"剩余时间"；
3. **损坏文件**：CRC 不过就抛 `SnapshotError`，宁可拒绝启动也不带病恢复。

## SAVE / BGSAVE / SHUTDOWN

- `SAVE`：同步写快照（tiny-redis 单线程，BGSAVE 退化为 SAVE，
  教程层面这是特性不是缺陷——想异步就得 fork 或子进程，见路线图）；
- `SHUTDOWN SAVE`：写快照后退出循环，不回包直接断开（与 Redis 一致）；
- `--snapshot-interval N`：数据变脏时每 N 秒自动快照（Redis 的
  save 规则的简化版）。

## 小结

- 绝对时间戳 + 惰性/主动双层过期 = Redis 同款语义；
- opcode 流 + CRC64 + 临时文件改名 = 简单但完整的快照方案；
- 恢复路径的边界情况（过期、损坏、截断）都要有测试兜底。
